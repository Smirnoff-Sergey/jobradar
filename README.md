# JobRadar

[![CI](https://github.com/Smirnoff-Sergey/jobradar/actions/workflows/ci.yml/badge.svg)](https://github.com/Smirnoff-Sergey/jobradar/actions/workflows/ci.yml)

Сервис поиска и оценки вакансий: собирает вакансии из открытых источников, фильтрует их по критериям, оценивает соответствие резюме с помощью LLM, присылает подходящие в Telegram и ведёт журнал откликов.

Проект в разработке. Готовы:

- этап 1 — каркас: API на FastAPI, PostgreSQL, миграции, JWT-авторизация, тесты и CI;
- этап 2 — сбор вакансий: адаптер getmatch, фоновые задачи Celery по расписанию, upsert без дублей, фильтр по критериям поиска;
- этап 3 — LLM-оценка вакансий по резюме: структурированный ответ модели, проверка схемой, дневной лимит запросов, только бесплатные модели. Цифры качества на реальном размеченном наборе пока нет — она появится после разметки;
- этап 4 — Telegram-бот на aiogram 3: вакансии с вердиктом `apply` приходят в Telegram ровно один раз, кнопки под сообщением ведут журнал откликов.

## Стек

- Backend: Python 3.13, FastAPI, SQLAlchemy 2 (async), asyncpg, Alembic, PostgreSQL
- Авторизация: JWT (access + refresh), хеширование паролей Argon2
- Фоновые задачи: Celery, Redis, Celery Beat
- Интеграции: getmatch, OpenRouter (OpenAI-совместимый API) — httpx, повторы с экспоненциальной задержкой; Telegram Bot API — aiogram 3 (polling или вебхук)
- LLM: структурированный ответ по JSON-схеме, проверка Pydantic, бесплатные модели
- Качество: pytest, ruff, mypy (strict), GitHub Actions
- Запуск: Docker Compose
- В планах: frontend на React и TypeScript, адаптер hh.ru

## Быстрый старт

```bash
cp .env.example .env
# впишите в .env секрет JOBRADAR_AUTH__JWT_SECRET:
python -c "import secrets; print(secrets.token_urlsafe(48))"
# для LLM-оценки — ключ OpenRouter в JOBRADAR_LLM__API_KEY (без ключа оценка выключена)
# для Telegram — токен бота от @BotFather в JOBRADAR_TELEGRAM__BOT_TOKEN (без токена бот выключен)

docker compose up -d --build --wait
docker compose exec api python -m app.cli create-user --email you@example.com
docker compose cp resume.txt api:/tmp/resume.txt
docker compose exec api python -m app.cli load-resume --email you@example.com --file /tmp/resume.txt
# ссылка для привязки чата Telegram: открыть и нажать «Start»
docker compose exec api python -m app.cli telegram-link --email you@example.com
```

Документация API: http://localhost:8000/docs

Регистрации нет: сервис рассчитан на одного владельца, пользователь создаётся командой `create-user`.

Compose поднимает PostgreSQL, Redis, одноразовый контейнер миграций, API, воркер Celery (очереди `celery`, `details`, `llm`, `notify`), Celery Beat и Telegram-бота. Beat запускает сбор по cron-выражению `JOBRADAR_COLLECTOR__SCHEDULE_CRON` (по умолчанию каждый час в :00 UTC), досыл оценок каждый час в :30 и досыл уведомлений каждые 10 минут; вручную — `POST /api/v1/sources/getmatch/run`. После создания пользователя откройте `GET /api/v1/search-profile`: профиль создастся с критериями по умолчанию и уже собранные вакансии перефильтруются.

> OpenRouter не обслуживает запросы с российских IP-адресов (ответ `403`). На сервере в России оценка уйдёт в паузу; качество можно проверять локально скриптом `scripts/eval.py`.

| `DELETE /api/v1/telegram/link` | Отвязать чат |
| `POST /api/v1/telegram/webhook` | Обновления от Telegram в режиме вебхука (секрет в заголовке `X-Telegram-Bot-Api-Secret-Token`) |

Все ошибки приходят в одном формате:

```json

```

## Как устроен сбор

1. **Загрузка.** Адаптер источника постранично забирает все актуальные вакансии. Сетевые запросы идут без открытой транзакции. Временные ошибки (таймаут, обрыв, `429`, `5xx`) повторяются с экспоненциальной задержкой и джиттером, `Retry-After` учитывается; остальные `4xx` не повторяются.
2. **Запись.** Одна короткая транзакция под advisory-блокировкой PostgreSQL: два параллельных сбора одного источника не перепишут данные друг друга. `INSERT … ON CONFLICT DO UPDATE` с условием по хешу содержимого — неизменившиеся вакансии не трогаются, повторный сбор не создаёт дублей. Вакансии, пропавшие из полного обхода, помечаются неактивными. Если обход вернул меньше 80% от числа активных вакансий или пустая страница пришла раньше конца выдачи, это считается сбоем источника, и деактивация не выполняется.
3. **Фильтр.** Новые и изменившиеся вакансии проверяются по критериям каждого пользователя: ключевые слова в названии, стоп-слова, удалёнка, тип оформления, минимальная зарплата на руки. Неизвестная зарплата или оформление не отсеивают, а помечаются.
4. **Описание.** Для всех прошедших фильтр вакансий без описания ставится задача загрузки карточки — не только для новых, поэтому потерянная или упавшая задача дозапросится при следующем сборе. Задачи идут в отдельную очередь `details` с ограничением темпа (`rate_limit`) и повторяются при временных сбоях; 404 запоминается как «описания нет». Задача идемпотентна.

## Как устроена LLM-оценка

Оценивается пара «вакансия — активное резюме»: вакансия прошла фильтр, описание загружено. Задача ставится сразу после загрузки описания, пропущенные пары подбирает часовой досыл.

1. **Захват.** Перед запросом в `evaluations` создаётся строка `pending` — уникальный индекс `(вакансия, резюме, версия промпта)` не даёт двум задачам оценить одну пару. Зависший захват (воркер упал) через 30 минут перехватывается.
2. **Лимит.** Перед каждым запросом атомарно резервируется место в дневном счётчике (`INSERT … ON CONFLICT … WHERE requests < limit`, по умолчанию 35 в сутки UTC при 50 у бесплатного тарифа OpenRouter). Лимит исчерпан — оценка откладывается до следующих суток.
3. **Запрос** идёт вне транзакции. Ответ проверяется схемой Pydantic: балл 0–100, вердикт, согласованный с баллом (`apply` ≥ 70, `maybe` 40–69, `skip` < 40), совпадения, пробелы, стоп-факторы. Невалидный ответ — одна повторная попытка, затем `failed`. Токены учитываются по всем попыткам.
4. **Переоценка** (`force`) заменяет прежнюю оценку только успешной новой. Смена текста вакансии или резюме сбрасывает их оценки — досыл пересчитает.

Промпт версионируется (`PROMPT_VERSION`): при изменении текста старые оценки сохраняются, новые пишутся отдельно. Резюме и вакансия передаются внутри тегов `<resume>` и `<vacancy>`, и модель предупреждена, что это данные, а не инструкции; текст вакансии не может закрыть тег.

**Только бесплатные модели** — правило зашито в код, а не только в настройки:

- настройки не принимают модель без суффикса `:free`;
- в запросе — `max_price: 0`, и OpenRouter сам отсекает платные маршруты;
- ответ без сведений о стоимости или со стоимостью больше нуля считается нарушением: оценка останавливается совсем до ручного снятия (`python -m app.cli llm-unpause`).

Отказ в доступе (`401`/`403`: ключ, регион) ставит оценку на паузу на час, чтобы не тратить лимит на заведомо провальные запросы. Провайдерам, которые сохраняют данные и обучаются на них, запросы не направляются (`data_collection: deny`) — в запросе текст резюме.

## Как устроен Telegram-бот

1. **Привязка.** `telegram-link` (или `POST /api/v1/telegram/link`) выдаёт ссылку `t.me/<бот>?start=<код>`. Код одноразовый, действует 15 минут, в БД хранится только его SHA-256. Бот получает `/start <код>` и записывает чат пользователю; один чат принадлежит одному пользователю. Кто напишет боту без кода, ничего не получит. `/stop` отвязывает чат.
2. **Что уходит.** Оценки с вердиктом `apply` по активному резюме, сделанные после привязки: старые вакансии при первой привязке не рассылаются. Задача ставится сразу после оценки, пропущенное (бот был недоступен) подбирает досыл.
3. **Ровно один раз.** Перед отправкой в `notifications` создаётся строка `pending` с уникальным ключом `telegram:<пользователь>:<вакансия>` — повтор задачи, досыл и переоценка не пришлют вакансию второй раз. Сама отправка идёт вне транзакции. Временный сбой (сеть, `5xx`, `429`) снимает захват, задача повторяется; если сообщение дошло, а ответ потерялся, повтор пришлёт дубль — потерять вакансию хуже. Бот заблокирован (`403`) — чат отвязывается, остальным пользователям рассылка продолжается. Отозванный токен (`401`) задачу не повторяет: вакансии дошлёт досыл, когда токен заменят.
4. **Кнопки.** «Откликнусь» и «Не подходит» создают или меняют отклик в журнале (`applications`), каждая смена статуса пишется в `status_history`; выбранная кнопка отмечается в сообщении. Кнопки меняют только ранние статусы: нажатие в старом сообщении не откатит «пригласили» или «отказ», выставленные через API. «Открыть» — ссылка на вакансию.

Бот работает в режиме polling отдельным контейнером (`python -m app.bot`): публичный адрес не нужен. Для вебхука задайте `JOBRADAR_TELEGRAM__MODE=webhook` и `JOBRADAR_TELEGRAM__WEBHOOK_SECRET`, зарегистрируйте адрес командой `python -m app.cli telegram-webhook --url https://<host>/api/v1/telegram/webhook` — обновления примет API теми же обработчиками.

## Качество оценки

```bash
# выгрузить вакансии для разметки (из БД с собранными вакансиями)
python -m app.cli export-eval-set --out vacancies.jsonl --limit 20
# проставить в каждой строке label: apply / maybe / skip, затем
cd backend
python -m scripts.eval --dataset vacancies.jsonl --resume resume.txt --out results.jsonl
```

Скрипт считает долю совпадений вердикта с разметкой и отдельно — совпадение решения «откликаться или нет», строит матрицу ошибок и записывает ответы модели построчно (сбой не теряет полученное). В отчёте — дата, версия промпта и модели. В репозитории есть демо-набор из пяти придуманных вакансий (`backend/scripts/eval_demo`); цифра на нём не показательна, реальный набор хранится вне репозитория.

## Устройство backend

```
backend/
  app/
    api/            # роуты FastAPI, зависимости, обработчики ошибок
    core/           # настройки, ошибки, JWT и пароли, HTTP-клиент с повторами
    db/             # модели SQLAlchemy, создание движка и сессий
    domain/         # чистая логика без БД и сети: фильтр, схема оценки
    llm/            # клиент LLM, промпт, оценка одной вакансии, набор и метрики качества
    repositories/   # доступ к БД
    services/       # бизнес-логика
    schemas/        # схемы Pydantic для API
    sources/        # адаптеры источников вакансий
    tasks/          # приложение Celery и задачи
    telegram/       # бот: клиент Bot API, тексты и кнопки, обработчики
    bot.py          # запуск бота в режиме polling
    cli.py          # служебные команды
  migrations/       # Alembic
  scripts/          # eval.py — проверка качества оценки
  tests/
```

Слои связаны в одну сторону: `api`, `tasks` и `cli` → `services` → `repositories`. Точки входа не обращаются к БД напрямую. Репозитории делают `flush`, транзакцию завершает (`commit`) сервис.

Ошибки предметной области (`app/core/errors.py`) не знают про HTTP: статусы назначает `app/api/errors.py`. У ошибок внешних сервисов есть признак `retryable` — по нему решается, повторять ли запрос и задачу.

Задачи Celery — тонкие обёртки: каждая запускает `asyncio.run` и создаёт движок БД без пула, потому что соединения asyncpg привязаны к event loop. API ставит задачи через интерфейс `TaskQueue` и не зависит от Celery; в тестах его заменяет фейк, поэтому Redis для тестов не нужен. Клиент LLM скрыт за протоколом `LLMClient` — провайдер меняется без правки бизнес-логики; так же сервисы уведомлений видят только протокол `TelegramClient`, а исключения aiogram переводятся в ошибки проекта.

## Разработка

Нужны [uv](https://docs.astral.sh/uv/) и PostgreSQL для интеграционных тестов. Ключ LLM и токен бота для тестов не нужны.

```bash
cd backend
uv sync

uv run ruff format .
uv run ruff check .
uv run mypy

# интеграционные тесты пересоздают схему в указанной БД, поэтому её имя обязано оканчиваться на _test
export JOBRADAR_TEST_DATABASE_URL=postgresql+asyncpg://jobradar:jobradar@localhost:5432/jobradar_test
uv run pytest --cov
```

Без `JOBRADAR_TEST_DATABASE_URL` выполняются только юнит-тесты, интеграционные пропускаются. В CI (`CI=true`) отсутствие переменной — ошибка, а не пропуск.

Как устроены тесты:

- схема тестовой БД создаётся миграциями Alembic, так что миграции проверяются на каждом прогоне;
- отдельный тест сверяет модели с миграциями: если поменять модель и забыть миграцию, он упадёт;
- каждый тест идёт внутри транзакции, которая откатывается после теста, даже если код вызывал `commit()`;
- внешние HTTP-запросы (getmatch, OpenRouter) мокаются через `respx`, LLM — фейковым клиентом; сеть в тестах не нужна;
- обработчики бота проверяются через диспетчер aiogram с подменённой сессией Bot API: обновление на входе, вызовы API на выходе;
- задачи Celery проверяются целиком: настоящий `asyncio.run`, своя сессия БД, замоканные внешние сервисы.

Хуки pre-commit: `uv run --directory backend pre-commit install`.
