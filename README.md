# JobRadar

[![CI](https://github.com/Smirnoff-Sergey/jobradar/actions/workflows/ci.yml/badge.svg)](https://github.com/Smirnoff-Sergey/jobradar/actions/workflows/ci.yml)

Сервис поиска и оценки вакансий: собирает вакансии из открытых источников, фильтрует их по критериям, оценивает соответствие резюме с помощью LLM, присылает подходящие в Telegram и ведёт журнал откликов.

Проект в разработке. Готовы:

- этап 1 — каркас: API на FastAPI, PostgreSQL, миграции, JWT-авторизация, тесты и CI;
- этап 2 — сбор вакансий: адаптер getmatch, фоновые задачи Celery по расписанию, upsert без дублей, фильтр по критериям поиска.

## Стек

- Backend: Python 3.13, FastAPI, SQLAlchemy 2 (async), asyncpg, Alembic, PostgreSQL
- Авторизация: JWT (access + refresh), хеширование паролей Argon2
- Качество: pytest, ruff, mypy (strict), GitHub Actions
- Фоновые задачи: Celery, Redis, Celery Beat
- Интеграции: getmatch (httpx, повторы с экспоненциальной задержкой)
- Запуск: Docker Compose
- В планах: адаптер hh.ru, LLM-оценка, Telegram-бот на aiogram 3, frontend на React и TypeScript

## Быстрый старт

```bash
cp .env.example .env
# впишите в .env секрет JOBRADAR_AUTH__JWT_SECRET:
python -c "import secrets; print(secrets.token_urlsafe(48))"

docker compose up -d --build --wait
docker compose exec api python -m app.cli create-user --email you@example.com
```

Документация API: http://localhost:8000/docs

Регистрации нет: сервис рассчитан на одного владельца, пользователь создаётся командой `create-user`.

Compose поднимает PostgreSQL, Redis, одноразовый контейнер миграций, API, воркер Celery и Celery Beat. Beat запускает сбор по cron-выражению `JOBRADAR_COLLECTOR__SCHEDULE_CRON` (по умолчанию каждый час в :00 UTC); вручную — `POST /api/v1/sources/getmatch/run`. После создания пользователя откройте `GET /api/v1/search-profile`: профиль создастся с критериями по умолчанию и уже собранные вакансии перефильтруются.

## API

| Метод и путь | Назначение |
|---|---|
| `GET /api/v1/health` | Проверка живости API и БД (`503`, если БД недоступна) |
| `POST /api/v1/auth/login` | Вход по email и паролю, выдаёт пару токенов |
| `POST /api/v1/auth/refresh` | Новая пара токенов по refresh-токену |
| `GET /api/v1/auth/me` | Текущий пользователь (заголовок `Authorization: Bearer <access>`) |
| `GET /api/v1/search-profile` | Критерии поиска (при первом запросе создаются по умолчанию) |
| `PUT /api/v1/search-profile` | Сохранить критерии и перефильтровать вакансии в фоне |
| `GET /api/v1/vacancies` | Вакансии с решением фильтра: `status=passed\|rejected\|all`, `source`, `active_only`, `limit`, `offset` |
| `GET /api/v1/vacancies/{id}` | Вакансия с полным описанием |
| `GET /api/v1/sources` | Источники и итог последнего сбора |
| `POST /api/v1/sources/{code}/run` | Запустить сбор вне расписания (`202` и id задачи) |
| `GET /api/v1/tasks/{id}` | Статус фоновой задачи |

Все ошибки приходят в одном формате:

```json
{"error": {"code": "invalid_credentials", "message": "Неверный email или пароль"}}
```

## Как устроен сбор

1. **Загрузка.** Адаптер источника постранично забирает все актуальные вакансии. Сетевые запросы идут без открытой транзакции. Временные ошибки (таймаут, обрыв, `429`, `5xx`) повторяются с экспоненциальной задержкой и джиттером, `Retry-After` учитывается; остальные `4xx` не повторяются.
2. **Запись.** Одна короткая транзакция под advisory-блокировкой PostgreSQL: два параллельных сбора одного источника не перепишут данные друг друга. `INSERT … ON CONFLICT DO UPDATE` с условием по хешу содержимого — неизменившиеся вакансии не трогаются, повторный сбор не создаёт дублей. Вакансии, пропавшие из полного обхода, помечаются неактивными. Если обход вернул меньше 80% от числа активных вакансий или пустая страница пришла раньше конца выдачи, это считается сбоем источника, и деактивация не выполняется.
3. **Фильтр.** Новые и изменившиеся вакансии проверяются по критериям каждого пользователя: ключевые слова в названии, стоп-слова, удалёнка, тип оформления, минимальная зарплата на руки. Неизвестная зарплата или оформление не отсеивают, а помечаются.
4. **Описание.** Для всех прошедших фильтр вакансий без описания ставится задача загрузки карточки — не только для новых, поэтому потерянная или упавшая задача дозапросится при следующем сборе. Задачи идут в отдельную очередь `details` с ограничением темпа (`rate_limit`) и повторяются при временных сбоях; 404 запоминается как «описания нет». Задача идемпотентна.

## Устройство backend

```
backend/
  app/
    api/            # роуты FastAPI, зависимости, обработчики ошибок
    core/           # настройки, ошибки, JWT и пароли, HTTP-клиент с повторами
    db/             # модели SQLAlchemy, создание движка и сессий
    domain/         # чистая логика без БД и сети (фильтр вакансий)
    repositories/   # доступ к БД
    services/       # бизнес-логика
    schemas/        # схемы Pydantic для API
    sources/        # адаптеры источников вакансий
    tasks/          # приложение Celery и задачи
    cli.py          # служебные команды
  migrations/       # Alembic
  tests/
```

Слои связаны в одну сторону: `api` и `tasks` → `services` → `repositories`. Роуты и задачи не обращаются к БД напрямую. Репозитории делают `flush`, транзакцию завершает (`commit`) сервис.

Ошибки предметной области (`app/core/errors.py`) не знают про HTTP: статусы назначает `app/api/errors.py`. У ошибок внешних сервисов есть признак `retryable` — по нему решается, повторять ли запрос и задачу.

Задачи Celery — тонкие обёртки: каждая запускает `asyncio.run` и создаёт движок БД без пула, потому что соединения asyncpg привязаны к event loop. API ставит задачи через интерфейс `TaskQueue` и не зависит от Celery; в тестах его заменяет фейк, поэтому Redis для тестов не нужен.

## Разработка

Нужны [uv](https://docs.astral.sh/uv/) и PostgreSQL для интеграционных тестов.

```bash
cd backend
uv sync

uv run ruff format .
uv run ruff check .
uv run mypy

# интеграционные тесты пересоздают схему в указанной БД, поэтому её имя обязано оканчиваться на _test
export JOBRADAR_TEST_DATABASE_URL=postgresql+asyncpg://jobradar:jobradar@localhost:5432/jobradar_test
uv run pytest --cov
```

Без `JOBRADAR_TEST_DATABASE_URL` выполняются только юнит-тесты, интеграционные пропускаются. В CI (`CI=true`) отсутствие переменной — ошибка, а не пропуск.

Как устроены тесты:

- схема тестовой БД создаётся миграциями Alembic, так что миграции проверяются на каждом прогоне;
- отдельный тест сверяет модели с миграциями: если поменять модель и забыть миграцию, он упадёт;
- каждый тест идёт внутри транзакции, которая откатывается после теста, даже если код вызывал `commit()`;
- внешние HTTP-запросы мокаются через `respx` на сохранённых ответах, сеть в тестах не нужна;
- задачи Celery проверяются целиком: настоящий `asyncio.run`, своя сессия БД, замоканный источник.

Хуки pre-commit: `uv run --directory backend pre-commit install`.
